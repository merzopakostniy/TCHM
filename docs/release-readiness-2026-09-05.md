## Блокирующие проблемы

### 1. Служебный токен принимается как токен входа — ИСПРАВЛЕНО

`backend/index.py:232` — `_read_token` проверяет подпись и срок JWT, но не его
назначение. `backend/index.py:958` — `_auth` отклоняет `disabled`, однако
принимает `pending`.

Локально подтверждено: подписанный токен с `act=verify` и `sub` ожидающего
подтверждения ТЧМ принимается как Bearer; `_can_edit_column` разрешает запись.
Это не подделка подписи и не доказательство доступа к чужой почте: проблема
именно в отсутствии разделения типов токенов и допуска только активных
профилей. Аналогично нужно исключить токены восстановления из API-сессий.

Перед выпуском: различать access/verify/reset/signup/state, требовать
корректные обязательные claims и `status == active` во всех защищённых
маршрутах, включая `/me`. Добавить негативные тесты.

### 2. Режим обслуживания не ограничивает запросы сервера — ИСПРАВЛЕНО

`backend/index.py:1650` — маршруты читают пользователя, затем сразу вызывают
обработчики данных. Флаги `app_config` читаются только через `/lock` и не
проверяются при чтении или изменении колонн и сотрудников.

Локальный вызов `GET /columns` вернул 200, ни разу не прочитав `app_config`.
Запрет администратору менять сам флаг работает; применение уже установленного
флага к операциям данных отсутствует.

Перед выпуском: централизованно применять `readsBlocked` и `writesBlocked`,
сохранив разработчику возможность снять блокировку, и проверить запросы
напрямую к API, а не только видимость элементов интерфейса.

### 3. Создание колонны может перезаписать существующую — ИСПРАВЛЕНО

`backend/index.py:1152` — при POST идентификатор строится из депо и номера,
затем выполняется UPSERT (`:1180`). Проверка существования есть только при
редактировании по ID. Повторный POST с тем же номером может заменить название
и сведения о руководителе существующей колонны.

Перед выпуском: атомарное создание с ошибкой конфликта для занятого номера;
отдельная операция редактирования. Проверить повторный и конкурентный POST.

### 4. Release-путь не закреплён, остаётся старый Firebase-вход — ИСПРАВЛЕНО

`lib/main.dart:59` — без `YANDEX_API=true` сборка выбирает Firebase. README
по-прежнему рекомендует команды без этого флага. Проверенный AAB собран с
правильным флагом, однако обычная команда сборки создаст другой вариант.

В локальных `firestore.rules:115`, `:141`, `:164` профиль разработчика может
создаваться по полям, которые задаёт клиент. Пароль разработчика проверяется
на клиенте (`lib/main.dart:2311`), а не этими правилами. Соответствие этих
локальных правил текущим опубликованным Firebase-правилам здесь не проверялось.

Перед выпуском: закрепить серверный режим в воспроизводимом release-процессе,
исключить старый способ выдачи привилегий и проверить, нужен ли ещё доступ к
Firebase у ранее выпущенных клиентов. Не менять старую рабочую базу без плана
перехода.

## Исправление №1: токены доступа и активный профиль

Опубликовано 05.09.2026 в Yandex Cloud, версия `d4eulasmih96eeq2hm4c`.
Предыдущая версия: `d4esodcf1a5o10nsluio` (возврат к ней вернёт уязвимость).

Новые токены входа содержат `act=access`. Сервер требует `act`, `sub`, `iat`
и `exp`, проверяет назначение, непустой строковый идентификатор и сроки.
Служебные токены verify/reset/signup/state и прежние токены без назначения
отклоняются. Ошибочные claims возвращают отказ, а не исключение обработчика.

`_auth` и `/me` допускают только `active`. Обычный вход и вход через Яндекс
также не выдают сессию для неизвестного или неактивного статуса. Права и депо
по-прежнему читаются из базы, а не из JWT.

Проверено: 32 серверных теста (22 прежних и 10 новых, включая матрицы
служебных токенов и защищённых маршрутов). После публикации `/health`
доступен; `/me`, `/columns`, `/machinists` отклоняют невалидный токен с 401.
Настройки функции, ADMIN_EMAILS и ссылки Lockbox сохранены.

Пользователям нужно повторно войти: старые сессии без `act=access` больше
не принимаются. Файлы клиента на этом шаге не менялись.

## Исправление №2: серверное применение режима обслуживания

Опубликовано 05.09.2026, версия `d4ep6itfvfe5fo8037oc`.
Предыдущая версия `d4eulasmih96eeq2hm4c` не применяет блокировку к данным.

Перед каждым запросом `/columns`, `/machinists` и `/users` сервер читает
актуальные флаги `app_config`, без кэширования:

- `writesBlocked`: чтение разрешено по обычным правам, любые изменения
  рабочих данных и управление пользователями запрещены всем, включая разработчика.
- `readsBlocked`: чтение запрещено всем, кроме разработчика; запись запрещена
  всем независимо от значения `writesBlocked`.
- Отказ возвращает HTTP 503, понятный текст и код `maintenance_full` или
  `maintenance_read_only`. Обработчик данных при отказе не вызывается.
- `/lock` доступен для чтения активным пользователям; менять его может только
  разработчик, в том числе во время полной блокировки.
- `/health`, собственный профиль `/me` и маршруты аутентификации остаются
  доступны. Регистрация, подтверждение почты и восстановление пароля не относятся
  к блокировке рабочих данных. Служебные операции через IAM остаются отдельным
  каналом обслуживания.

Клиент проверяет режим при входе и перед обновлением данных, показывает экран
технических работ с кнопкой «Проверить доступ». При полном отказе очищает
списки в памяти репозитория. Разработчик сохраняет экран депо и управление
блокировкой. Режим не доставляется push-сообщением: уже показанные данные
на открытом экране не исчезают мгновенно; сервер отклоняет следующие запросы.
Проверка флагов выполняется перед обработчиком: уже начавшаяся операция может
завершиться после переключения режима.

Проверено: 38 серверных тестов, включая матрицу из 160 сочетаний ролей,
маршрутов и флагов, снятие блокировки, изменение режима между запросами и
отказ при ошибке чтения конфигурации. 20 тестов Flutter прошли, включая экран
обслуживания, возврат после разблокировки, доступ разработчика и очистку
кэша при смене режима между HTTP-запросами. `flutter analyze` — без замечаний.
Матрица блокировки проверена локально через HTTP-обработчик с тестовыми JWT
и заглушкой БД; рабочую базу для проверки не блокировали.
После публикации подтверждены новая активная версия, неизменность настроек
функции и оба флага `false`; `/health` вернул 200, защищённые маршруты с
невалидным Bearer — 401.

Приложение в Android-эмуляторе обновлено горячим перезапуском. Release AAB
из первоначальной проверки предшествует этой правке и требует пересборки

## Исправление №3: создание и редактирование колонн

Опубликовано 05.09.2026, версия `d4eps9b6tkl1ipn3eoon`.
Предыдущая версия `d4ep6itfvfe5fo8037oc` ещё допускала перезапись при POST.
Активная версия и сохранность настроек подтверждены; `/health` вернул 200,
GET/POST `/columns` с невалидным Bearer — 401.

POST теперь использует `INSERT`, поэтому занятой первичный ключ внутри депо
не перезаписывается. Сервер возвращает HTTP 409 с текстом «Колонна №… уже
существует в этом депо». Обрабатываются оба сообщения конфликта YDB:
`insert_pk` и фактически полученное от Query Service `Conflict with existing key`.
Остальные ошибки базы не маскируются под конфликт номера.
[Семантика INSERT в документации YDB](https://ydb.tech/docs/ru/yql/reference/syntax/insert_into).

PUT использует `UPDATE ... WHERE id = $id AND depot_id = $depot RETURNING id`.
Он не создаёт запись заново, если её удалили после предварительной проверки;
в этом случае возвращается 404. Права и ограничение депо сохранены. Проверка
номера отклоняет bool, дробные числа и значения вне положительного Uint32.

Проверено: 44 локальных серверных теста и интеграционная проверка реальной YDB
через `backend/check_column_creation.py`. Она перенаправляет запросы обработчика
в отдельную таблицу с уникальным именем, созданную по схеме колонн, и удаляет
её в `finally`. Подтверждены сохранность первой записи после повторного POST,
одинаковые номера в разных депо, редактирование, 404 для отсутствующей записи
и пять пар одновременных созданий: каждый раз один результат 200, один 409,
в базе одна запись с данными победившего запроса. Таблица удалена.
Рабочие таблицы эта проверка не читает и не меняет.

ID существующих записей и нумерация не мигрировались. Проверка защищает
ключ создания `{depot}_column_{number}`; общий аудит старых импортированных
ID и перенумерации остаётся отдельной задачей.

Следующий шаг: закрепить release-конфигурацию и исключить старую выдачу
привилегий через Firebase (пункт 4).

## Исправление №4: рабочая конфигурация и старые привилегии Firebase

Клиент исправлен: обычный `flutter run` использует Yandex API. Release/profile
также всегда выбирают API независимо от старых YANDEX_API/FIREBASE_CONFIGURED

## Исправление №5: администратор при восстановлении пароля

Опубликовано в Yandex Cloud 05.09.2026, версия `d4eob8uu96sn76nh0vjd`.
Pending-профиль после подтверждения почты ссылкой reset получает роль из
ADMIN_EMAILS, одинаково для viewer и tchm. У активного профиля роль сохраняется;
заблокированные и неизвестные статусы не активируются. Адрес и исходная роль
берутся из базы, а не из тела запроса. UPDATE одновременно меняет пароль,
статус и роль, проверяя прежние email/status/role; удалённый профиль не создаётся
заново, при параллельном изменении возвращается 409.

52 серверных теста прошли. После публикации подтверждены активная версия и
неизменность настроек, `/health` — 200, неверный Bearer на `/me` — 401,
неверная ссылка POST `/auth/reset` — 400. Письма и пароли реальных пользователей
в рамках проверки не отправлялись и не изменялись.
