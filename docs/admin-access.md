# Администратор приложения

Роль `admin` работает со всеми депо: сводка, колонны, сотрудники, экспорт,
список учётных записей, отключение/включение доступа и удаление учётных записей.
Она не может менять режим обслуживания (`PUT /lock`) и управлять учётной
записью разработчика. Назначение ролей остаётся служебной операцией IAM,
доступной владельцу Yandex Cloud, а не пользовательскому API.

В приложении возможности разделены на `canManageAllDepots`,
`canManageAccounts` и `canManageDatabaseLock`. Последняя есть только у
разработчика. Сервер проверяет роль из базы на каждом запросе.

## Назначение после регистрации

В конфигурации функции `tchm-api` переменная `ADMIN_EMAILS` содержит адреса,
которым владелец разрешил роль администратора после подтверждения почты.
Для текущего назначения: `kutulovsv@transport.mos.ru` (регистр не важен).

Пользователь проходит обычную регистрацию с ключом своего депо. До
подтверждения адреса запись имеет статус `pending` и обычную роль. После
перехода по ссылке из письма сервер назначает `admin`. При регистрации через
Яндекс ID используется только почта из подписанного сервером пропуска.
Передача роли `admin` или другого email в теле регистрации прав не даёт.

Повторное открытие ссылки подтверждения у активной записи не восстанавливает
ранее снятую роль. Отключённую запись ссылка не активирует.
Для отмены будущих назначений адрес нужно убрать из `ADMIN_EMAILS`;
для уже существующей записи отдельно изменить роль служебной операцией
`set_role`. Не заменять остальные переменные окружения и ссылки Lockbox.

## Проверка

- `flutter test` — права клиента и кнопка обслуживания только у разработчика.
- `python -m unittest backend.test_admin_permissions` с зависимостями из
  `backend/requirements.txt` — права сервера, изоляция депо, запрет блокировки,
  защита разработчика и назначение только после подтверждения адреса.

Рабочее окружение — Yandex Cloud по умолчанию, отдельный флаг не нужен.
Правила Firebase опубликованы отдельно и запрещают старым профилям без депо
доступ к рабочим данным; требуется новая регистрация в приложении.

## Подтверждение через восстановление пароля

Восстановление по действующей ссылке из письма также подтверждает почту.
Если профиль ещё pending, сервер применяет ADMIN_EMAILS: KutulovSV получает
admin независимо от первоначального выбора viewer/tchm. Используется адрес
из записи базы; email и роль в теле запроса не дают привилегий.

Уже активный аккаунт сохраняет свою текущую роль, поэтому восстановление
пароля не возвращает ранее снятые права. Disabled/неизвестный статус запрещён.
Пароль, статус и роль меняются одним UPDATE с проверкой прежних роли,
статуса и почты: параллельное закрытие доступа или удаление профиля не
отменяется сбросом пароля. При изменении профиля возвращается 409.
